# Stellar contract compatibility and library reuse

Source audit on 2026-09-29 for the PR #2166 replacement. No changes to `sushi/stellar`, the installed SDK, or either contract repository are required by these recommendations. Stellar-specific glue belongs in this monorepo. **Live read-only checks confirm that the configured manager and factory pool implementation still use the older negative-tick rounding; a small local adapter is required before reusing SDK tick conversion for those contracts.**

## Source identity is not deployment identity

The current repository heads are **not identical to the active deployed builds**. Further inspection of the downloaded WASM found seven manager methods present in current periphery source but absent from the live manager exports. The live factory also embeds Soroban SDK 23.0.2 metadata, while current core resolves SDK 23.5.3. The pool hash is associated with the older June build in the first-party deployment record. See the [deployment identity report](stellar-deployment-verification.md) for the refreshed hashes and the distinction between build-record evidence and independently reproduced binaries.

The arithmetic tests and manager simulation below verify specific behavior. They do not establish equivalence of every function in either repository to every deployed contract.

## What can be reused

The contracts use several V3 arithmetic formulas, but equivalence must be established per operation. Being exported from `sushi/evm` neither proves nor disproves suitability for a Stellar calculation.

| Operation | Reuse decision | Evidence and boundary |
| --- | --- | --- |
| Integer human-price representation | Reuse `Price` from `sushi`. | Token-decimal adjustment is rational arithmetic before encoding the core's Q64.96 initialization price. [Core initialization](https://github.com/sushi-labs/sushi-stellar/blob/21ab5ae31600cc86ccf676bfd706b716d31c847a/contracts/dex-pool/src/init.rs#L77) accepts that encoded integer, not a human decimal string. |
| Initial square-root encoding | Reuse `encodeSqrtRatioX96`; the unused local Newton square-root implementation has been removed. | The frontend needs floor(sqrt(raw ratio) × 2^96), followed by the core's bounds check. Exact encoding inequalities are checked in the existing local math tests. |
| Liquidity from two raw token budgets | Reuse `maxLiquidityForAmounts(..., false)` for its integer arithmetic. | Periphery [token0](https://github.com/sushi-labs/sushi-stellar-periphery/blob/c5985292b3b62abb95d6287d1ac0d0e96c3cacf8/contracts/libraries/src/liquidity_amounts.rs#L24) first floors `a*b/Q96`; [token1 and side selection](https://github.com/sushi-labs/sushi-stellar-periphery/blob/c5985292b3b62abb95d6287d1ac0d0e96c3cacf8/contracts/libraries/src/liquidity_amounts.rs#L44) use the same formulas and boundaries as the installed helper. ## What must remain local

**Deposit caps are not the same quantity as core mint charges.** For token0, the manager calculates liquidity as `floor(amount0 * floor(a*b/Q96) / (b-a))`. The minimum desired cap supporting a chosen liquidity is therefore `ceil(L*(b-a)/floor(a*b/Q96))`. Returning the core charge `ceil(L*Q96*(b-a)/(a*b))` can lose liquidity when the manager calculates it again. Keep the small inversion/composition helper in `stellar/_common/lib/utils/liquidity-amounts.ts`, using library integer helpers. This follows directly from the [manager formula](https://github.com/sushi-labs/sushi-stellar-periphery/blob/c5985292b3b62abb95d6287d1ac0d0e96c3cacf8/contracts/libraries/src/liquidity_amounts.rs#L32) and [core charge](https://github.com/sushi-labs/sushi-stellar/blob/21ab5ae31600cc86ccf676bfd706b716d31c847a/contracts/amm-math/src/sqrt_price_math.rs#L248). It is why replacing the local helper with an EVM position's `mintAmounts` is inappropriate.

Keep strict amount parsing and Stellar limits locally. Desired amounts are `u128` in the [manager parameters](https://github.com/sushi-labs/sushi-stellar-periphery/blob/c5985292b3b62abb95d6287d1ac0d0e96c3cacf8/contracts/manager/src/nonfungible_position_manager.rs#L366), but actual token transfers are `i128`, and the core [requires liquidity to fit a positive i128](https://github.com/sushi-labs/sushi-stellar/blob/21ab5ae31600cc86ccf676bfd706b716d31c847a/contracts/dex-pool/src/mint.rs#L64). An unbounded JavaScript bigint calculation does not enforce either ABI limit. The parser can reuse `parseUnits` after rejecting excess fractional precision; permitting a library to silently round user input changes their requested amount.

There are two further contract constraints worth distinguishing:

- **Intermediate liquidity:** the manager converts each token's supported liquidity to `u128` [before selecting the minimum](https://github.com/sushi-labs/sushi-stellar-periphery/blob/c5985292b3b62abb95d6287d1ac0d0e96c3cacf8/contracts/libraries/src/liquidity_amounts.rs#L70). A frontend must not assume a small final minimum proves both computations are representable. A sentinel budget used internally to derive a paired amount is not an actual submitted cap; validate the final pair, not that sentinel.
- **Per-tick capacity:** core [derives an absolute maximum from the tick spacing](https://github.com/sushi-labs/sushi-stellar/blob/21ab5ae31600cc86ccf676bfd706b716d31c847a/contracts/dex-pool/src/tick.rs#L25), then [checks the aggregate liquidity already using each boundary](https://github.com/sushi-labs/sushi-stellar/blob/21ab5ae31600cc86ccf676bfd706b716d31c847a/contracts/dex-pool/src/tick.rs#L151). A static quote can enforce the absolute maximum, but remaining capacity requires current pool state / simulation.

Form state, price orientation, presets, errors, wallet signatures, trustline handling, and create-then-mint retry behavior also remain application concerns.

The implementation keeps the strict parser and imports the existing library arithmetic. Dead `encodePriceSqrt`/`integerSqrt` code has been removed. The local tick adapter lives in `stellar/_common/lib/utils/ticks.ts`, so no SDK changes are needed.

## Factory, fee, ordering and initialization findings

The frontend's supported fees match the factory constructor exactly: **500 → spacing 10, 3000 → spacing 60, 10000 → spacing 200**. These integer fees correspond to 0.05%, 0.3% and 1%; source comments calling them “basis points” are imprecise. The [constructor values](https://github.com/sushi-labs/sushi-stellar/blob/21ab5ae31600cc86ccf676bfd706b716d31c847a/contracts/dex-factory/src/lib.rs#L265) and [fee validation](https://github.com/sushi-labs/sushi-stellar/blob/21ab5ae31600cc86ccf676bfd706b716d31c847a/contracts/dex-factory/src/fees.rs#L119) establish the actual behavior. Factory owners may enable additional tiers, but cannot overwrite an already-enabled tier's spacing; restricting the creation form to the three defaults is a supported-product choice, not a protocol-wide list.

The factory sorts token addresses and stores both lookup orders. The frontend nevertheless must define every price/range in canonical token1/token0 order. Manager [sorting swaps token amounts but leaves tick inputs unchanged](https://github.com/sushi-labs/sushi-stellar-periphery/blob/c5985292b3b62abb95d6287d1ac0d0e96c3cacf8/contracts/manager/src/nonfungible_position_manager.rs#L599); passing reversed human-price ticks and relying on manager sorting would be wrong. The replacement page orders tokens before constructing its form, and submission loads the pool's canonical tokens.

The actual factory [create_and_initialize_pool entrypoint](https://github.com/sushi-labs/sushi-stellar/blob/21ab5ae31600cc86ccf676bfd706b716d31c847a/contracts/dex-factory/src/lib.rs#L476) atomically creates and initializes a missing pool, initializes an existing uninitialized one, and preserves the price of an already-initialized pool. This is the entrypoint used by the frontend. The separate periphery `PoolInitializer` helper is not the frontend's transaction path. The manager's [mint](https://github.com/sushi-labs/sushi-stellar-periphery/blob/c5985292b3b62abb95d6287d1ac0d0e96c3cacf8/contracts/manager/src/nonfungible_position_manager.rs#L723) is a later transaction, so creation success followed by mint failure remains a real partial-success case.

The position manager independently reads `slot0` and tick spacing at execution and checks the deadline and minimum token amounts. The existing frontend sends zero minimum amounts. That preserves existing behavior, but source verification does not make it price-movement protection. See [manager checks](https://github.com/sushi-labs/sushi-stellar-periphery/blob/c5985292b3b62abb95d6287d1ac0d0e96c3cacf8/contracts/manager/src/nonfungible_position_manager.rs#L628).

## Revision issue and deployment limits

The core change [“Fix tick math negative rounding parity”](https://github.com/sushi-labs/sushi-stellar/commit/a3ecac324b85ddafdeec60527c32898c53e1ee0a) was committed on 2026-07-06. It adds one square-root unit whenever the old negative-tick conversion had a remainder. The current core matches the SDK behavior checked in the [previous exhaustive audit](stellar-liquidity-math-verification.md). The periphery's checked-in lock still selects the earlier core implementation, and its manager actually [calls that linked tick function when quoting mint liquidity](https://github.com/sushi-labs/sushi-stellar-periphery/blob/c5985292b3b62abb95d6287d1ac0d0e96c3cacf8/contracts/manager/src/nonfungible_position_manager.rs#L639). Thus “current core and checked-in periphery are identical to SDK V3 math” is not supported by the sources.

A concrete source-derived incompatibility occurs at an exact negative lower boundary: initialize a current-core pool at SDK `sqrtRatioAtTick(-60)` and request range `[-60, 60]` with token0 only. The frontend/current core consider that price exactly at the lower boundary. The locked manager computes a lower boundary one square-root unit smaller, considers the price strictly inside the range, and obtains zero liquidity from the zero token1 budget. Core mint rejects zero liquidity. This example follows from the linked tick and liquidity functions; it is not a claim about which revision is deployed.

This difference can alter a negative range boundary and the resulting integer liquidity. Do not silently pick a deployment model from the repository names or replace verified current-core tick math with legacy rounding everywhere. The pool and manager can have different build revisions, and both matter: the manager determines liquidity; the pool determines the eventual charges.

The core repository contains a [historical mainnet upgrade record](https://github.com/sushi-labs/sushi-stellar/blob/21ab5ae31600cc86ccf676bfd706b716d31c847a/upgrade-artifacts/MAINNET_FLASH_REMEDIATION_HUMAN_READABLE_UPGRADE_LOG_2026-06-05.md#L37) naming commit `956725a274eae4a79dfea68c99dd2c05dccc1e14` and a pool WASM hash. That June record does not prove the currently deployed manager or pool build. Periphery's [checked-in fixture documentation](https://github.com/sushi-labs/sushi-stellar-periphery/blob/c5985292b3b62abb95d6287d1ac0d0e96c3cacf8/contracts/manager/test-fixtures/README.md#L11) only says its pool/factory WASMs came from the core main branch; it does not pin their source commits. Passing its fixture tests alone would not resolve the deployment question.

Raw local evidence: `/tmp/stellar-contract-sources/active-contracts.json`, `active-manager-math.json`, `active-{factory,manager,xlm-usdc-pool}.wasm`; the two `.cjs` scripts alongside them reproduce the reads using the installed SDK and the existing `DRPC_ID` environment variable. **Implementation consequence:** keep a minimal adapter in the monorepo that derives legacy negative-tick results from SDK `TickMath` by subtracting one for negative ticks other than the special minimum tick, and adjusts the inverse conversion at those shifted boundaries. Continue to reuse the verified liquidity, price and integer helpers. Do not switch to current-core behavior until the configured deployed contracts change accordingly.

The live test resolves the material rounding question for the configured manager and the factory's default pool implementation at the recorded ledgers. It is not a full byte-for-byte source reproduction of the manager binary, an audit of every existing pool, or a funded mint test. Contracts can be upgraded; these results must be rechecked when configured addresses or executable hashes change.
